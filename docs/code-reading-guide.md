# 第一次阅读 Persona AI 代码

本项目中，人物是可被引用的档案，不是多个独立 Agent。默认体验是直接聊天；Harness 负责约束执行、管理上下文、记录状态和控制费用。

## 先沿着一条消息看

建议先看普通聊天，再看可选的检索、报告和演练分支。

1. **页面输入**：`src/relationship_agent/persona_web/app.js` 的 `send()`。首次发送创建会话，再提交消息。网络中断后复用幂等键，避免重复创建同一任务。
2. **HTTP 接口**：`src/relationship_agent/beta/app.py` 的 `/api/message`。认证、来源校验和输入检查完成后交给 `Service.submit()`，立即返回任务 ID。
3. **准备上下文**：`src/relationship_agent/beta/service.py` 的 `submit()` 调用 `store.py` 识别人物，读取确认记忆及可用历史，冻结本次任务的输入快照。紧急安全回应或人物澄清可以不调用模型。
4. **后台执行**：`Service.claim()` 领取任务，再由 `execute()` 调用 `engine.py`。worker token 防止过期线程覆盖结果。
5. **模型回答**：`engine.py` 的普通路径调用 `respond`，一次返回意图和聊天回答。具体规则在 `prompts.py`，协议调用在 `providers.py`，返回字段及来源检查在 `schemas.py`。
6. **按需继续**：知识和证据问题才调用相应检索；明确要求报告或演练时才走专门阶段。已有检查点可用于恢复，不必从头重复成功阶段。
7. **保存与显示**：`ScopedStore.finish()` 提交结果与分层记录；前端 `poll()` 读取过滤后的 `public_run()`，交给 `renderChat()` 展示。

普通路径不等于每次必定只有一次 HTTP 请求：失败重试、结构修复、完全重复回复的修复都可能增加尝试次数，并受预算约束。

## 容易混淆的字段

| 字段或概念 | 含义及边界 |
| --- | --- |
| `user_id` | 账号数据范围。不能由客户端随意指定其他账号。 |
| `session_id` / `sid` | 一次持续聊天的容器；同一个人物可出现在不同会话中。 |
| `person_id` / `person_ids` | 当前话题涉及的人物。档案与已确认事件可跨会话引用。 |
| `run_id` / `rid` | 一次输入对应的后台任务，不是整段会话。 |
| `epoch` / `context_epoch` | 账号记忆版本。纠错后旧聊天仍可展示，但旧版本不再送入新模型上下文。 |
| `kind` | 执行/结果类型，用来选择分支和展示形式，不是另一个模型的名称。 |
| `state` | 中间检查点及冻结上下文，供恢复执行；不是公开接口应原样返回的内容。 |
| `result` | 最终回答及其结构化补充信息，公开展示前仍经过过滤。 |
| `generation` | 仅前端使用的请求代数，切换会话后让旧异步响应失效；与数据库 epoch 不同。 |
| `attempt` | 一次模型 HTTP 尝试。重试也需要计入次数与预算。 |

## “保存聊天”和“记住人物”不同

- **聊天记录**：用于让用户回看。是否能再次送给模型，还要检查人物范围、记忆版本、任务状态和长度。
- **人物档案**：昵称、别名、职业、用户印象等背景，不能当作对方性格或未来行为的证明。
- **人物事件**：待确认候选不会直接成为长期记忆；确认表示用户认可这条陈述，不表示事件已被外部核实。
- **工作流记录**：`observation`、`inference`、`simulation` 分层保存。假设和演练不能升级为真实发生的经历。
- **删除依赖**：删除人物或事件会清理相关会话，防止已删除内容从旧回答中再次被引用。不要绕过 `ScopedStore` 直接删一行。

这些行为主要看 `beta/store.py`，对应回归集中在 `tests/test_persona.py` 和 `tests/test_harness.py`。

## 辅助文件怎么读

| 目录/文件 | 阅读重点 |
| --- | --- |
| `beta/database.py` | 表、外键与短事务锁；改结构需要考虑迁移。 |
| `beta/auth.py`、`beta/config.py` | 身份与配置边界，和具体回复内容无关。 |
| `academic.py`、`knowledge.py` | 外部学术搜索和本地关键词卡片；都不等于读过论文全文。 |
| `demo.py`、`routing.py` | 固定演示回复和演示路由，不代表真实模型能力。 |
| `protocols.py` | 执行器依赖的存储接口，便于替换实现与测试。 |
| `agent_loop.py`、`model_client.py`、顶层启动文件 | 兼容旧导入或启动方式，不是重复维护另一套系统。 |
| `scripts/` | 配置、验收、构建、备份；真实模型调用脚本是 `live_smoke.py`，不会被默认验收自动运行。 |
| `evals/` | 合成案例与评测；结构通过不等于建议质量通过。 |
| `tests/` | 模块开头说明它防止哪类问题，类和测试名称用于定位行为。 |
| `Dockerfile`、`compose.yaml`、`Caddyfile`、`render.yaml` | 部署方式与数据持久化；配置文件存在不代表已上线。 |
| `.env.example` | 配置字段说明；真实 `.env`、数据库与备份不纳入注释整理或提交。 |

### JSON 案例为什么没有行内注释

标准 JSON 不允许注释，`evals/cases.json` 保持有效 JSON：

- `id`：稳定案例标识，用于比较报告和指定特殊断言。
- `language`：场景语言。
- `message`：合成用户输入。
- `review`：人工审阅标准；不能把保存了这个字段当作已经完成评价。

双语多轮案例在 `evals/persona_cases.py`：每项提供中文、英文问题及 rubric，评测分别在有人物事件和仅有档案的条件下运行。

## 维护时遵循的原则

注释重点解释输入边界、状态变化、副作用和取舍，不逐行翻译代码。调整行为时同步改注释及对应测试，不能只让说明“看起来更完整”。

具体检查命令与现存技术债见 [代码维护规范](maintenance.md)；部署步骤见 [部署文档](deployment.md)；测试与模型质量的区别见 [评测说明](evaluation.md)。
